# 앱 업데이트

웹·서버 배포는 기존 GitHub main 검증 후 같은 Cloudflare Worker에 반영한다. 출퇴근 DB·기기 연결·서명 키는 바꾸지 않는다. 네이티브 앱 자체의 변경은 기존 서명으로 APK 릴리스를 만들고 설치해야 한다. 일반 화면·계산 기능의 변경에는 APK 재설치가 필요 없다.

## 사용자가 보는 흐름

1. 앱 시작·온라인 복귀·화면 복귀 및 약 5분 간격으로 새 웹 버전을 확인한다. 새 파일은 먼저 별도 서비스워커 캐시에 준비한다.
2. 태블릿은 60초 이상 입력이 없고, 저장·전송·연결 코드 입력·미전송 큐·다른 대화상자가 없는 시점에 적용을 시도한다. 관리자는 알림의 적용 버튼으로 시작하며 작성 중인 양식이 있으면 보류한다.
3. **업데이트가 있습니다**와 5초 카운트다운을 표시한다. **나중에**를 누르면 자동 적용을 10분 미루고 직접 적용은 가능하다. 활성화 직전에 안전 조건을 다시 확인한다.
4. 활성화 후 화면을 새로고침한다. 새 서비스워커가 알려주는 실제 버전을 확인한 뒤 **업데이트가 반영되었습니다**에 변경 내역을 모아 표시한다. 미전송 기록과 태블릿 토큰 저장소는 삭제하지 않는다.
5. 여러 릴리스를 건너뛰면 새 항목들을 한 대화상자에 묶는다. 목록만 세로 스크롤하며 확인 버튼은 아래에 남는다. 확인한 내용은 다시 팝업하지 않는다. 상단 종 아이콘에서 내역을 다시 볼 수 있다.

첫 설치는 ‘방금 업데이트 완료’로 표시하지 않는다. 실패·시간 초과를 성공으로 기록하지 않는다. 동일 릴리스 ID로 코드만 바뀌면 새 파일이 반영됐다는 일반 안내를 표시한다. 다른 탭이 서비스를 활성화해도 입력 중인 현재 탭을 강제로 새로고침하지 않는다. 저장 공간 제한으로 알림 이력 저장이 실패해도 출퇴근 저장·전송은 독립적으로 동작한다. 다만 영구 이력 저장이 불가능한 기기에서는 다음 실행의 확인 이력을 보장할 수 없다.

업데이트 대기 알림은 접을 수 있고 일반 양식 대화상자 위에 겹치지 않는다. 다운로드 페이지에서는 APK 링크를 가리는 대기 알림을 표시하지 않는다. 최초 설치의 서비스워커 연결 이벤트를 실제 새 버전 활성화로 오인하지 않도록 버전을 비교한다.

이 안내를 포함하지 않은 구버전 JavaScript는 새 안내 코드를 실행할 수 없다. 이번 기능을 받은 뒤의 업데이트부터 사전 안내가 동작한다. 배포 즉시 모든 화면을 강제로 재시작하는 방식이 아니며, 오프라인·입력·미전송 대기 중에는 지연될 수 있다. 서버 API는 배포 즉시 바뀌므로 이전 화면이 열려 있어도 사용할 수 있도록 하위 호환성을 유지한다.

## 다음 릴리스 작성

- `shared/app-releases.ts` 맨 앞에 새 ID·날짜·제목·변경 항목을 추가한다. 공개 정보만 넣고 ID는 재사용하거나 기존 항목의 의미를 바꾸지 않는다. 최근 30개 이내로 관리한다.
- 빌드는 해시 버전의 `sw.js`와 `app-release.json`을 함께 생성한다. 메타데이터와 HTML에는 재검증/캐시 금지 정책을 적용한다. API·APK는 서비스워커 캐시에 넣지 않는다. 직전 캐시는 이전 화면의 파일 접근을 위해 하나 보관한다.
- `npm run check` → `npm run android:package` → `npm run cloud:check` → Node·Cloudflare 브라우저 테스트를 순차 실행한다. 서비스워커 테스트가 dist 파일을 잠시 바꾸므로 동시에 빌드하거나 다른 브라우저 테스트를 실행하지 않는다.
- GitHub CI가 검증한 동일 dist를 배포한다. 현재 main보다 오래된 실행은 운영 배포를 건너뛴다. 배포 후 `/api/health`, `/app-release.json`, APK·사이트 연결 정보를 확인한다.
